## Ledger-core extraction follow-up

The current source implements the first extraction scoped below. The eleven
pure modules now live in `packages/ledger-core/src/ledger_core/`, with one
canonical definition and explicit `ledger.*` compatibility re-exports. Their
definitions retain the baseline behavior; internal and production consumer
imports use `ledger_core`.

The core distribution declares only Pydantic. Root application, agent and
legacy ledger manifests declare their direct core dependency. The agent
replaces its ledger distribution dependency with `ledger-core` and an explicit
FastMCP dependency for its existing MCP client adapter. That adapter remains
in place, so the entire agent distribution is not infrastructure-free.

`tests/packaging/test_ledger_core.py` builds and installs the wheel outside the
workspace, then exercises imports, schema/JSON fixtures and exact calculations
with isolated Python and no legacy ledger, database or MCP libraries installed.
The architecture checks cover every core module; compatibility checks compare
the canonical and legacy exported objects. Docker workspace copies, backend CI
path selection, lint commands and the unit CI job include the new package and
packaging suite.

Installed-only verification also exposed the agent wheel's earlier missing
`klaudia/` namespace. Its build mapping now preserves that namespace and packaged
runtime skills while retaining the existing editable source layout. A focused
wheel-content check prevents the source checkout from masking that failure.

Execution/storage functions retain their implementation, including approval
enforcement, ownership/revision checks, original operation references and
caller-held task-lock connections. Existing schema/checkpoint, calculation,
API, ledger and process-recovery checks remain the regression surface. Exact
commands and results belong to the code PR; this follow-up does not claim a
remote CI result. The baseline assessment and acceptance criteria below are
retained to explain the scope and remaining module work.

## Current dependencies

| Caller | Dependency | Consequence for migration |
| --- | --- | --- |
| `klaudia/core/agent/` | Pure ledger request/value types, errors, calculations and evidence helpers | Import isolation exists; package independence is the next step |
| `app/services/core/`, catalogue and workflow | Agent protocols plus concrete ledger execution/storage | Composition adapters must preserve ownership and connection scope |
| `klaudia/interfaces/tool_registry.py` | FastMCP client | The current agent distribution contains an infrastructure adapter |
| Authentication and extraction | `AppDBClient` under extraction | Identity persistence cannot be relocated as if it were already independent |
| Workflow and memory stores | asyncpg and startup schema SQL | Separate rule ownership from storage before relocating packages |

Ledger code does not import `app`, `klaudia` or `config`; the architecture checks
enforce that direction. They also prohibit app/config imports from the agent
package and persistence imports from its core. Framework use is more specific:
the current agent core uses LangChain, while the MCP client adapter uses FastMCP.
A package move must account for both rather than declaring the entire existing
`klaudia` distribution infrastructure-free.

## First extraction: installable ledger core

At the recorded baseline, the next problem was distribution coupling. The
[agent manifest](https://github.com/Yudhyy/Klaudia/blob/5a33e394748c9a1c7863488402acfa8b96780bd7/klaudia/pyproject.toml)
declares `mcp-ledger`, whose
[manifest](https://github.com/Yudhyy/Klaudia/blob/5a33e394748c9a1c7863488402acfa8b96780bd7/mcp-ledger/pyproject.toml)
includes asyncpg and FastMCP even when a caller only needs proposal validation or
deterministic calculations. The extraction scope puts that pure code in
`packages/ledger-core/src/ledger_core/`.

The initial scope is the existing pure import closure:

| Modules under `mcp-ledger/ledger/` | Responsibility |
| --- | --- |
| `append_contracts.py`, `authoring_contracts.py` | Append and table-authoring requests and validation |
| `resources.py`, `errors.py`, `evidence.py` | Resource contracts, shared failures and bounded evidence |
| `query.py`, `grid.py`, `calculations.py`, `financial_contracts.py` | Query/calculation contracts and pure grid aggregation |
| `typed_contracts.py`, `formula_engine.py` | Typed edits and native exact-decimal formula validation/evaluation |

These eleven modules depend on the standard library and Pydantic at this
revision. Keep their existing module structure initially; the larger target tree
does not require rewriting them into entities, repositories or use cases.
Database-backed execution, operation/approval storage, MCP authorization and the
MCP host remain in their current locations for this slice. This is the first
part of ledger-core, not the completed ledger migration.

Keep one canonical definition for every moved type and function. Existing
`ledger.*` paths re-export those definitions so exception handling, model
identity and callers using the old paths remain compatible. The core must not
import back through those compatibility modules.

The agent-owned `OperationExecutor`, `CatalogueReader` and `AuthoringReader`
interfaces already exist. Preserve them and their behavior. Their ledger DTO
dependency is an explicit transitional rule in the
[target](target.mdx#dependency-rules); translating consumer-owned requests in
composition adapters is later work. Keep financial validation in ledger code.

### Acceptance criteria

1. Build the core wheel and install it in a fresh environment outside the
   workspace with only its declared dependencies. Its public imports and pure
   calculation checks work without the repository on `sys.path`, without the
   legacy ledger distribution, and without PostgreSQL, FastMCP or MCP installed.
   Blocked-import checks remain additional protection, not a substitute.
2. Preserve the six existing schema/JSON baselines in
   [the contract fixture](https://github.com/Yudhyy/Klaudia/blob/5a33e394748c9a1c7863488402acfa8b96780bd7/tests/unit/fixtures/ledger_proposal_contracts.json),
   proposal rejection rules, legacy import identity, stored operation payloads
   and agent checkpoint round trips. Add a failing package-isolation check before
   changing package ownership.
3. Preserve exact decimal arithmetic and current query, typed-value and formula
   semantics. Existing grid, aggregation, calculation, financial-contract and
   formula tests exercise the moved implementation through its public imports.
4. Retain authenticated ownership, revision checks, approval binding and expiry,
   idempotent execution, original operation references and atomic effect/receipt
   commits. Run the relevant API/ledger and process-recovery regressions against
   verified isolated test stores.
5. Update uv workspace membership, direct consumer dependencies, the lockfile,
   Docker manifest copies, import-check paths, Ruff commands and CircleCI path
   selection together. Verify installed-package imports and API, worker and MCP
   entrypoints. Removing the agent's `mcp-ledger` dependency must also account
   for the FastMCP client adapter it currently contains; declare its real
   dependency or relocate it rather than relying on the root install.
6. Extend import enforcement to the full extracted package and retain current
   agent/ledger direction checks. No core module imports persistence, transports,
   composition/settings, or the old `ledger` implementation.

## Preserve transaction ownership

[TaskConnection and TaskSession](https://github.com/Yudhyy/Klaudia/blob/5a33e394748c9a1c7863488402acfa8b96780bd7/app/services/workflow/store.py)
use the connection holding the task advisory lock for checked ledger writes.
Their operation methods and the standalone
[OperationService](https://github.com/Yudhyy/Klaudia/blob/5a33e394748c9a1c7863488402acfa8b96780bd7/app/services/core/operations.py)
call the same ledger functions through different connection adapters. The task
adapter also supplies approval policy and checks session ownership.

This coupling protects recovery. A later adapter must retain the caller-held
connection; opening a different pool inside an operation module changes the
contract. Each financial effect and receipt commit together. An entire model run
is not one database transaction. Recovery reuses the original stored operation
reference rather than reconstructing a proposal from a new model response.

[Durable-task tests](https://github.com/Yudhyy/Klaudia/blob/5a33e394748c9a1c7863488402acfa8b96780bd7/tests/integration/api/test_durable_tasks.py)
and [process-kill tests](https://github.com/Yudhyy/Klaudia/blob/5a33e394748c9a1c7863488402acfa8b96780bd7/tests/integration/api/test_process_recovery.py)
provide the regression surface for this contract.

## Remaining ownership work

### Identity persistence

[Authentication routes](https://github.com/Yudhyy/Klaudia/blob/5a33e394748c9a1c7863488402acfa8b96780bd7/app/routes/v1/auth.py)
still use `container.db_client`. The
[shared database client](https://github.com/Yudhyy/Klaudia/blob/5a33e394748c9a1c7863488402acfa8b96780bd7/app/services/extraction/infra/db_client.py)
implements user creation, credential lookup and last-login updates alongside
conversation, document and extraction-cache storage.

When identity work starts, isolate those identity operations using the current
pool and schema. Preserve authentication responses, password handling, token
behavior and conflict handling. Conversation sessions are not authentication
sessions. Account deletion and token invalidation remain the separate behavior
requested by [issue #9](https://github.com/Yudhyy/Klaudia/issues/9).

### Schema upgrades

`AppDBClient.connect`, `LedgerStore.connect`,
`MemoryDocumentStore.initialize` and `TaskStore.connect` still execute schema SQL.
No versioned migration setup exists in the reviewed paths. Before schema-changing
work or relocating those stores, define upgrade ownership and process startup
order, retaining the ledger's standalone initialization contract. Issue #9
already requires an upgrade path for installed databases; the target's Alembic
layout does not establish that a migration framework has been selected.

### Workflow, memory and documents

Make durable task coordination and memory-document ownership explicit as in the
[target](target.mdx#module-ownership). The agent defines the continuation payload;
workflow persists it and coordinates resume and human decisions. Ledger enforces
financial approval and preconditions at execution. Memory owns context documents
and their revisions, while ledger remains authoritative for financial effects.

Document extraction now has a clear queued-outcome interface, but that interface
still contains asyncpg and the shared `AppDBClient`. Preserve the saved-outcome
rules and their
[integration tests](https://github.com/Yudhyy/Klaudia/blob/5a33e394748c9a1c7863488402acfa8b96780bd7/tests/integration/extraction/test_outcomes.py)
when separating document application logic from its database/queue adapters.

The [migration sequence](target.mdx#migration-sequence) follows the pure
ledger slice with the remaining capability adapters and moves
functioning modules with their startup and checks. Documentation-site work under
#4 and object-store naming under #5 remain independent. Each code slice needs its
own review and regression evidence; this assessment does not establish a
completed package layout or a runtime pass.
